# Programming with Pixels：让 AI 看着 IDE 写代码

> 论文：*Programming with Pixels: Can Computer-Use Agents do Software Engineering?*
> 来源：[arXiv:2502.18525](https://arxiv.org/abs/2502.18525)

---

## 一、这篇论文在问什么？

现有的编码智能体（SWE-agent、Agentless、OpenHands）都依赖**专门设计的文本 API**——AST 解析器、IPython 内核、结构化搜索工具。它们从不"看"IDE 界面。

而计算机使用智能体（CUA）擅长**看截图、点按钮**，但评测都停留在网页浏览、系统设置这类简单任务。

PwP 的问题很直接：**能不能让一个通用 CUA 只靠看截图和操作键鼠，像人一样在 VSCode 里写代码、调试、跑测试？** 如果不行，差距到底在哪？

---

## 二、环境设计

PwP 让智能体通过**截图 + 原始键鼠事件（xdotool）**控制一个运行在 Docker 中的 VSCode IDE，形式化为部分可观测马尔可夫决策过程（POMDP）：

- **动作**：原始键盘/鼠标操作（点击坐标、输入文字、快捷键）
- **观测**：屏幕截图 + Set-of-Marks（SoM）标注的可交互元素
- **验证**：基于执行结果（测试通过、编译成功），不依赖人工评判

这个设计有几个值得注意的特点：

1. **表达力完整**：不限制动作类型，智能体可以打开任何菜单、使用任何 IDE 功能
2. **工具全开放**：调试器、linter、重构工具都在 IDE 里，智能体可以通过视觉界面使用它们
3. **语言和模态无关**：支持 Python、Java、JS、Lean 等多种语言，也支持图片/PDF 作为输入

---

## 三、基准：PwP-Bench

从 13 个已有数据集 + 2 个新任务中构建了 5400 个实例，**PwP-Bench-Lite** 包含 300 个实例（每任务 20 个）用于高效评测。

| 类别 | 数据来源 | 典型任务 |
|:---|:---|:---|
| 代码生成与编辑 | HumanEval, SWE-Bench, DSBench, Res-Q | 修 bug、实现函数、编辑已有代码 |
| 多模态代码合成 | Design2Code, Chart2Mimic, SWE-Bench-MM | UI 截图→前端代码、图表→可视化代码 |
| 领域特定 | InterCode (CTF 黑客挑战), miniCTX (Lean 定理证明) | 动态分析、形式化验证 |
| IDE 配置与通用 SWE（新） | 新构建 | 改主题、装插件、性能分析、重构、调试标准库 |

任务覆盖面很广——从纯代码编辑到"看着设计图还原 UI"再到"在 IDE 里改设置"，测试的是智能体在不同视觉依赖程度下的表现。

---

## 四、实验：三种条件的对比

论文设计了三种智能体条件，在相同模型上对比：

1. **纯视觉 CUA**：只看截图 + 键鼠操作，和人类用 IDE 的方式一样
2. **CUA + File/Bash API**：视觉能力保留，但额外给两个文本 API（文件读写 + bash 命令）
3. **专用 SWE 智能体**（Mini-SWE-Agent）：纯文本交互，不用视觉

### 4.1 主要结果

| 条件 | 代码编辑 | 多模态 | 领域特定 | 通用 SWE | **总平均** |
|:---|:---:|:---:|:---:|:---:|:---:|
| 纯视觉 CUA（Claude-4.0） | 16.0% | 38.1% | 6.7% | 37.5% | **22.9%** |
| CUA + File/Bash（Claude-4.0） | 53.4% | 58.6% | 43.3% | 37.5% | **50.7%** |
| 专用 Mini-SWE-Agent（Claude-4.0） | 49.4% | 60.3% | 40.0% | 37.5% | **48.8%** |

纯视觉条件下的所有模型都很差。最好的 Claude-4.0 也只有 22.9%，Gemini-Flash 低至 1.1%。

但加上**仅仅两个文本 API**，Claude-4.0 直接跳到 50.7%，**反超了专用智能体**（48.8%）。

### 4.2 各模型纯视觉表现

| 模型 | 代码编辑 | 多模态 | 领域特定 | 通用 SWE | **总平均** |
|:---|:---:|:---:|:---:|:---:|:---:|
| Claude-4.0 Sonnet | 16.0% | 38.1% | 6.7% | 37.5% | **22.9%** |
| Claude-3.7 Sonnet | 11.8% | 28.5% | 8.3% | 27.5% | **17.7%** |
| Claude-3.5 Sonnet | 10.7% | 8.3% | 5.0% | 22.5% | **10.5%** |
| GPT-4o | 0.8% | 12.4% | 1.7% | 10.0% | **5.3%** |
| Gemini-Pro | 2.5% | 5.7% | 0.0% | 7.5% | **3.5%** |
| Qwen2.5-VL-72B | 0.0% | 4.3% | 0.0% | 5.0% | **1.8%** |
| Gemini-Flash | 0.0% | 4.3% | 0.0% | 0.0% | **1.1%** |

Claude 系列明显领先，且 7 个月内性能翻倍（3.5 → 4.0）。

## 五、深入分析：为什么纯视觉这么差？

### 5.1 视觉定位失败是头号杀手

论文统计了 Claude-4.0 的轨迹，发现 **95% 的轨迹中至少有一次视觉定位错误**：

- **点错元素**：想点"运行"按钮，结果点了旁边的图标
- **幻觉内容**：看到屏幕上并不存在的输入框，对着空气输入
- **无法解读视觉线索**：linter 的红色下划线就在眼前，但智能体视而不见
- **Set-of-Marks 不够用**：即使标注了可交互元素的位置，错误率仍然很高

更致命的是**错误恢复能力差**：出错后，智能体倾向于忽略当前屏幕状态，按记忆中的动作序列继续执行——就像闭着眼睛走路，撞墙了还继续往前走。

### 5.2 不会用 IDE 的高级工具

VSCode 里有调试器、性能分析器、重构工具，但纯视觉智能体**几乎从不主动使用它们**。即使能看到菜单入口，也不知道什么时候该用、怎么用。

论文做了一个"辅助实验"：直接给智能体提供 IDE 工具的 API 调用（如"重命名符号"），结果 Design2Code 任务从 48.1% 跃升至 **79.5%**。这说明工具本身不是问题，**发现和使用工具的能力**才是。

### 5.3 不同任务类型的行为差异

通过分析智能体的行为模式，论文发现：

- **HumanEval（纯代码生成）**：完全依赖 File API，几乎不用视觉编辑
- **Design2Code（UI 还原）**：大量使用视觉交互，频繁查看实时预览
- **VSCode 配置任务**：完全视觉操作（改主题、装插件）

这说明"视觉依赖程度"因任务而异，不能一概而论。

## 六、一个有趣的例外

在 InterCode-CTF（动态分析/黑客挑战）任务中，Claude-3.5 纯视觉 CUA 达到了 **100%** 的成功率，超过了专用 SWE-Agent 的 72%。

这暗示视觉交互在**需要动态观察运行状态**的场景中有独特优势——比如看终端输出、观察程序行为、根据运行时反馈调整策略。纯粹的文本 API 反而可能丢失这些有用的视觉信息。

---

## 七、与 CUA-SWE 的对比

PwP 和 CUA-SWE 几乎同期发表，都在探索编码与视觉交互的交叉地带，但视角不同：

| 维度 | PwP | CUA-SWE |
|:---|:---|:---|
| **核心问题** | CUA 能否替代专用编码智能体？ | 视觉反馈如何帮助软件工程？ |
| **交互方式** | IDE 内视觉操作（VSCode） | 代码编辑 + 截图 + GUI 交互 |
| **关键结论** | 给两个文本 API 就能追上专用智能体 | 视觉反馈对特定任务是刚需 |
| **视觉的角色** | 瓶颈——能绕过就绕过 | 不可替代——某些任务必须靠视觉 |
| **验证方式** | 测试用例 + 编译 | 确定性验证器（任务成功 + 无回归 + 变更合规） |

两篇论文看似矛盾（PwP 说"API 替代视觉"，CUA-SWE 说"视觉不可替代"），实际互补：

- **PwP 的任务以代码编辑为主**，视觉不是核心需求，所以用 API 绕过视觉是合理的
- **CUA-SWE 的 M 类任务需求只在界面中**（设计图纸、运行状态），视觉是核心需求，绕不过去

两篇论文的共同发现是：**当前 CUA 的视觉定位能力是主要瓶颈**。

## 八、个人评价

PwP 最大的贡献是**把问题拆干净了**。通过三种条件的对比，它清晰地展示了一个事实：CUA 做不好软件工程，不是因为"不够聪明"，而是因为"看不准"。给两个文本 API 就能从 22.9% 跳到 50.7%，超过专用智能体——这说明推理能力是够的，只是视觉执行拖了后腿。

95% 轨迹存在视觉定位错误这个数字很惊人。它意味着当前的多模态模型在复杂 UI 环境中的感知能力还远不够可靠。幻觉问题在代码编辑场景尤其致命——对着不存在的输入框输入文字，这种错误在人类开发者身上几乎不会发生。

不过，Claude 系列 7 个月翻倍的进步速度也说明这个方向在快速进化。如果视觉定位问题得到解决，CUA 的灵活性优势（能使用任何 IDE 功能、能观察运行时状态）可能会让它超越纯文本智能体。InterCode-CTF 上 100% vs 72% 的结果已经暗示了这种可能性。
